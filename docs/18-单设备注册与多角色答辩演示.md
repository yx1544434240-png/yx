# 单设备注册与多角色答辩演示

## 答辩操作顺序

1. 启动本地后端：显式使用 dev 配置及 `APP_DEV_MODE=true`，数据库账号按本机开发配置设置；不需要 Docker。
2. 手机开发版小程序微信登录，进入「我的 → 答辩演示 · 切换演示身份」。此入口需后端明确开启，体验版和正式版不显示。
3. 填写一个姓名，点击「创建演示新用户」。后端真实写入独立居民账号，小程序进入「完善注册资料」。
4. 选择建立本人老人档案、申请绑定家中长辈，或申请成为服务人员。老人和家属仍共用 RESIDENT 系统角色，通过档案与绑定区分业务权限。
5. 演示入驻时，填写姓名、本人手机号码、服务区域和服务经历，提交后显示待审核，账号仍为居民。
6. 电脑后台进入「服务人员 → 入驻申请审核」，查看申请资料，填写原因退回。手机刷新后补充说明，再次提交。
7. 后台重新打开当前申请，核对出发站点、经纬度后点击「审核通过并开通」。默认站点来自项目现有演示配置，实际服务时应按站点核对。
8. 手机点击「刷新审核结果 → 更新身份并进入工作台」。后端重新签发当前工作人员身份的 Token，进入工作台。
9. 在「我的 → 我的资质证明」提交证书，后台审核技能并安排班次后，再设置接单状态。入驻通过本身不会自动授予专业技能或开始派单。
10. 返回个人中心的演示入口，可继续切换预置老人、家属、工作人员，以及最近创建的演示用户。点击「返回微信登录」后重新微信登录，可返回原微信账号。

## 身份模型

一个 AppID 对应一个小程序；同一微信的真实 OpenID 不会因演示切换改变。演示创建的是项目自己的数据库测试账号，用户名为 `demo_reg_<32位请求标识>`，不绑定真实 OpenID，手机号初始为空。不会覆盖原微信账号，也不开放普通用户自行选择 ADMIN 或 STAFF 角色。

模拟的是身份入口，后续使用真实的资料保存、入驻申请、审核、角色开通和资质业务。创建按钮携带幂等请求标识，网络重试复用该标识；若需要另一位新用户，再次进入演示页创建即可。已有切换接口只允许预置居民/家属/工作人员和符合命名规则的演示账号，拒绝普通真实账号、管理员和停用账号。

新用户引导也适用于真实微信首次注册；已有微信账号正常进入原业务页面。有明确登录前目标的用户会继续原流程，个人中心始终保留入驻申请入口。

本阶段每个账号只有一个系统角色。入驻通过将居民账号转为工作人员，不同时提供两个正式身份。答辩中的居民与工作人员业务请使用不同演示账号。

## 审核与一致性

- 每个账号只有一条入驻申请。仅 REJECTED 状态可修改重提，PENDING/APPROVED 不可重复提交。
- 申请材料包含 revision；管理员按打开时的版本审核，旧版本审核或重复审核会被拒绝。
- 提交与审核均锁定对应用户；通过审核、更新用户角色及资料、建立人员档案在同一数据库事务中完成。
- 审核通过需要站点名称及合法经纬度；手机号不能与其他账号冲突。任何一步失败，审核结果与身份变更一起回滚。
- 新工作人员默认 RESTING，人员档案为已通过；专业技能资质独立审核，原有派单条件继续生效。
- 切换身份使用统一会话更新，清除私有媒体临时缓存和待处理 Tab 参数；晚到的旧会话请求不会覆盖新身份。

## 接口

路径相对于 `/api`：

| 接口 | 访问条件 | 用途 |
| --- | --- | --- |
| GET /auth/demo-capabilities | 开发后端 + 登录居民/工作人员 | 查询演示入口是否开放 |
| GET /auth/demo-accounts | 同上 | 查询可切换测试账号，最多最近 50 条 |
| POST /auth/demo-register | 同上 | requestId、realName；只创建居民测试账号 |
| POST /auth/mock-login | 仅明确启用的 dev/test 后端 | 切换允许的演示账号 |
| POST /auth/refresh | 已登录账号 | 从数据库重新读取角色并签发 Token |
| GET /staff/applications/mine | 本人居民/工作人员 | 查看本人入驻申请 |
| POST /staff/applications/submit | 居民 | 提交或补充入驻资料 |
| GET /staff/applications/page | 管理员 | 按状态分页查看申请 |
| POST /staff/applications/audit | 管理员 | 审核、配置站点并开通身份 |

演示控制器受 `(dev | test) & !prod` 和 `app.dev-mode=true` 双条件限制；prod 即使误带 dev 参数也不注册演示控制器。入驻申请及审核是正常业务接口，正式环境可使用。

## 数据库与验证

现有数据库只需执行新增表脚本 `sql/migration_v7.sql`，可重复执行。新建空数据库使用更新后的完整 schema。2026-10-22 本机业务库已新增申请表，原有 9 个用户和 3 位工作人员保留；没有在业务库创建测试申请。

本次新增后端 11 项单元测试、小程序 8 项测试、后台审核组件 3 项测试，并使用本地 MySQL 执行完整接口与事务测试。

最终验证：后端 111 项单元测试、1 项本地 MySQL 完整流程测试，小程序 195 项测试、后台 44 项测试全部通过；后台生产构建、WXML/WXSS 编译及 110 组手机/平板布局检查通过。独立测试数据库已清理，业务库仍为原有 9 个用户、3 位工作人员，入驻申请表为空。

本地集成测试类为 `EnrollmentLocalIntegrationTest`：须显式设置 `AGEDCARE_LOCAL_INTEGRATION=true`、`AGEDCARE_TEST_DB_PASSWORD`（可选 `AGEDCARE_TEST_DB_USER`，默认 root），执行 Maven 的 `-Dtest=EnrollmentLocalIntegrationTest`。测试连接本机 MySQL，创建随机的 `agedcare_enrollment_test_<uuid>` 数据库，仅在其中建表和写入测试资料，结束后删除该专用库；不使用 Docker，不接触业务数据。

已验证未登录/越权拒绝、重复注册幂等、退回重提、旧版本审核拒绝、身份刷新、重复审核不重复建档，以及手机号冲突后的完整事务回滚。手机、平板及大字模式使用共享布局并经 CSS 检查；拍照、微信授权及真实设备网络仍需真机验收。

更新后需重启后端、重新编译小程序，再刷新后台页面。演示用户会保留在当前业务数据库，便于答辩继续使用；不提供清空真实账号或订单的重置按钮。
