# 数据库设计草案

文档状态：逻辑设计，尚未生成或执行建表脚本。字段类型、索引与迁移脚本在后端初始化时落实。

## 1. 通用约定

- 业务主键采用后端生成的长整型 ID，对前端序列化为字符串，避免 JavaScript 数值精度问题。
- 业务状态使用明确枚举码，接口、数据库和状态转换规则统一。
- 时间精度与时区约定统一；业务日期按北京时间计算。
- 金额使用 `DECIMAL`，单位为元；时长使用整数分钟。
- 历史订单、派单、履约及操作事实不物理删除；停用基础资料不影响历史查询。
- 日志不得保存登录凭证、完整令牌或不必要的个人资料。
- 服务地址等历史快照与当前档案区分保存；读取快照仍需经过权限校验。

## 2. 核心实体

| 表 | 关键字段与用途 | 主要约束 |
| --- | --- | --- |
| `sys_user` | 登录标识、主身份、启用状态 | 登录标识按实际登录方式建立唯一约束 |
| `elder_profile` | 本人账号（可空）、姓名、必要联系人、服务需求 | 本人账号关联不能被任意认领 |
| `family_binding` | 家属账号、老人、关系、审核状态、审核人 | 同一关系不能同时有多条有效授权 |
| `service_item` | 名称、说明、价格、预计分钟数、所需技能、上架状态 | 价格非负，服务时长为正 |
| `staff_profile` | 账号、服务区域、出发站点、审核状态 | 一个服务人员账号对应一份人员资料 |
| `staff_skill` | 人员、技能码、审核状态 | 同一人员与技能组合唯一 |
| `staff_shift` | 人员、日期、班次开始结束 | 结束晚于开始；有效班次不重复重叠 |
| `service_order` | 下单人、老人、服务快照、时间地点、状态、当前派单、版本号 | 订单号与请求幂等键唯一 |
| `dispatch_attempt` | 订单、轮次、候选人员、来源、期限、状态、各事件时间 | 轮次内尝试编号唯一；有效分配由事务维护 |
| `dispatch_score` | 订单、轮次、人员、筛选结果、分项指标、总分、算法版本 | 保存当次输入摘要与参数，不覆盖旧轮次 |
| `staff_booking` | 人员、订单、派单记录、计划时段、状态 | 派单记录唯一对应一条预留；时段冲突由事务校验 |
| `order_status_log` | 订单、旧状态、新状态、操作者、原因、时间 | 与实际状态转换同事务写入 |
| `service_record` | 订单、人员、实际起止时间、服务说明、可选凭证 | 一单一条主记录；修改留痕 |
| `service_review` | 订单、评价人、评分、文本 | 订单唯一；评分限定 1～5 |
| `service_complaint` | 订单、发起人、内容、处理状态、处理人、结果 | 权限由订单及授权关系校验 |
| `message_notification` | 接收人、业务事件键、内容、已读时间 | 事件与接收人组合幂等 |
| `operation_log` | 操作者、动作、目标、原因、发生时间 | 仅追加关键操作事实 |

上述为 17 张主要业务表。技能字典、项目技能关系、文件元数据和实验结果是否单独建表，在实现对应模块时确定；不以表数量作为设计目标。

## 3. 订单表重点字段

| 字段 | 含义 |
| --- | --- |
| `id`、`order_no` | 主键与对外订单号 |
| `requester_user_id` | 实际下单账号 |
| `elder_id` | 接受服务的老人 |
| `service_item_id` | 对应项目 |
| `service_name_snapshot` | 下单时服务名称 |
| `service_description_snapshot` | 下单时服务内容 |
| `required_skills_snapshot` | 下单时必要技能，防止项目修改影响历史解释 |
| `price_snapshot` | 下单时服务费用 |
| `duration_minutes_snapshot` | 下单时预计服务时长 |
| `planned_start_at`、`planned_end_at` | 预约起止时间 |
| `address_snapshot`、`longitude`、`latitude`、`coordinate_type` | 服务地址与统一来源坐标 |
| `contact_snapshot` | 本单必要联系信息，按权限读取 |
| `status` | 订单当前状态 |
| `current_dispatch_id` | 当前有效派单记录，空值表示无有效分配 |
| `dispatch_round` | 当前调度轮次 |
| `idempotency_key`、`request_digest` | 防重复创建，并识别相同键不同内容 |
| `version` | 并发条件更新版本号 |
| `created_at`、`updated_at` | 创建与修改时间 |
| `cancelled_at`、`cancel_reason` | 取消事实 |

客户端提交的服务费用、派单对象、订单状态和下单人 ID 不直接作为可信业务值。联系人快照应仅包含履约所需信息。

## 4. 派单与预留

派单记录状态：

| 状态 | 含义 |
| --- | --- |
| PENDING | 等待有效接单 |
| ACCEPTED | 曾有效接单且分配仍有效 |
| REJECTED | 人员拒单 |
| EXPIRED | 超时失效 |
| REVOKED | 因订单取消或人工改派而撤销 |

即使后续撤销，原来的 `accepted_at`、`revoked_at` 和原因也要保留。服务完成后保留该派单的接受事实，由订单与履约记录表达完成情况。

排班预留状态至少包括 HELD（待接单占用）、CONFIRMED（已接单占用）、RELEASED（已释放）、FINISHED（已履约）。当日负载统计需要纳入已完成服务的实际时长，不能只查询占用中的预留。

排班检查读取前后相邻任务，计算出行可行性；服务尚未结束时应结合实际履约状态识别延迟，不以计划结束时间自动释放人员。

## 5. 事务与并发约定

1. 为订单派单时，统一先锁订单，再锁所选人员记录。所有修改该人员排班与预留的入口遵循同一锁协议。
2. 持锁后重新检查订单状态、人员有效性、前后任务和预留冲突，再写派单、预留、订单状态及状态日志。
3. 单次派单事务只为一名候选创建预留，候选失效后退出本次尝试再选择下一人。需同时修改多人安排时，统一按人员 ID 升序加锁。
4. 接单、超时、取消和改派同时校验当前派单 ID、期望状态和相关期限，使用事务与条件更新确定唯一有效结果。
5. 通知依据已提交业务事实幂等生成；通知失败不回滚已经成立的接单事实，后续允许重试。
6. 普通唯一索引不能独立保证任意时间区间不重叠，必须保留事务中的人员级串行检查。

## 6. 索引方向

- 订单：下单人及创建时间、老人及创建时间、状态及预约开始时间。
- 派单：人员及状态、状态及接单期限、订单及轮次及尝试编号。
- 预留：人员及计划开始时间、订单、派单记录唯一键。
- 班次：人员及日期。
- 家属授权：家属及审核状态、老人及审核状态。
- 通知：接收人及已读状态及创建时间。

最终索引需结合接口查询和执行计划确认。订单快照、评分输入与日志应避免重复存储不必要的敏感字段。
