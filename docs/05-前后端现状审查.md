## 一、前端不足

### F1. 小程序快捷登录参数传错，正式登录入口也未接通（P1）

`profile.js` 将 `{ params: { username } }` 作为请求封装的第三个参数，但第三个参数实际是 header。用户名没有进入查询串或请求正文。后端无参数时默认选择管理员，因此不能可靠地按按钮切换老人、家属或服务人员；如果微信拒绝非字符串 header，请求还可能直接失败。

本地请求探针已确认用户名被放进 header，而 URL 和正文均没有用户名。当前小程序页面也未发现 `wx.login` 或正式账号登录调用。

位置：[profile.js](../miniprogram/pages/user/profile.js#L28)、[request.js](../miniprogram/utils/request.js#L47)。

修复：统一请求函数签名与调用，接通正式居民登录；演示入口仅在明确开启的演示环境存在。

### F2. 预约日期格式与后端契约不一致（P1）

小程序发送 `yyyy-MM-dd HH:mm:ss`，但当前 Spring Boot Jackson 配置没有为 `LocalDateTime` 增加对应解析器。用项目 Jackson 自动配置和自定义配置运行探针时，空格格式被拒绝，带 `T` 的 ISO 格式可以解析。`spring.jackson.date-format` 本身没有解决该字段的解析。

位置：[create.js](../miniprogram/pages/order/create.js#L126)、[JacksonConfig.java](../backend/src/main/java/com/agedcare/common/config/JacksonConfig.java)。

修复：统一使用 ISO 日期时间，或显式配置 `LocalDateTime` 序列化和反序列化格式，并用接口测试验证。

### F3. 新用户档案与首次家属绑定流程有断点（P1）

新增老人页面不提交本人关联，后端新增时也没有建立本人或受托关系；新建档案可能无法进入当前用户的 `/elders/my-list`，导致保存成功后仍不能选择该老人下单。

家属申请页面同样从 `/elders/my-list` 选择目标，该接口只返回本人或已经授权的老人。没有既有授权的新家属无法选择首次要申请绑定的老人。

位置：[elder-form.js](../miniprogram/pages/user/elder-form.js#L39)、[family.js](../miniprogram/pages/user/family.js#L33)、[ElderProfileService.java](../backend/src/main/java/com/agedcare/modules/elder/service/ElderProfileService.java#L96)。

修复：区分本人档案与代管建档，建立明确的归属或审核关系；首次绑定使用受控绑定码或管理员定向邀请，避免开放所有老人资料。

### F4. 履约记录使用假定时间，且缺少后端必填关联（P1）

服务开始时间固定为提交时刻减一小时，与实际点击开始服务无关。请求没有 `staffId`，后端也没有从有效接单人员补齐，但 SQL 将该字段定义为非空。按照当前请求与建表脚本，即使修正日期格式，首次记录插入仍缺少必填值。

位置：[workbench.js](../miniprogram/pages/staff/workbench.js#L127)、[FulfillmentService.java](../backend/src/main/java/com/agedcare/modules/fulfillment/service/FulfillmentService.java#L84)、[schema.sql](../sql/schema.sql#L271)。

修复：后端在开始服务时记录实际开始时间，提交时校验结束时间；人员 ID 根据当前有效分配推导并校验，不能由前端任意指定。

### F5. 重复提交与提交结果提示不可靠（P1）

每次点击提交都会创建新幂等键，提交按钮只有 loading，没有 disabled，函数也没有提交中短路检查。网络结果不明确后重试仍会换键，无法保证一次预约只生成一笔订单。

成功提示固定为“系统已派单”，没有根据返回订单的 WAIT_MANUAL、WAIT_DISPATCH 等实际状态区分。

位置：[create.js](../miniprogram/pages/order/create.js#L106)、[create.wxml](../miniprogram/pages/order/create.wxml)。

修复：同一次预约意图持有稳定请求键，禁用提交中的按钮；按服务器实际状态展示“预约已提交”或“等待社区安排”。

### F6. 管理后台调度队列可能漏单，自动重试不能恢复新轮次（P1）

调度页先获取全部订单的第一页 50 条，再在浏览器中筛选待人工与待派单状态。较早的异常订单可能被更新订单挤出第一页，管理员看不到。该页没有分页入口。

“重试自动派单”调用 `/dispatch/assign`，未创建新轮次；已达到本轮三次上限时，重试仍会立即转回待人工处理。

位置：[dispatch/index.vue](../admin-web/src/views/dispatch/index.vue#L129)。

修复：后端支持多状态查询并分页，按预约时间排序；明确区分当前轮重试与开始新调度轮次。

### F7. 服务人员工作台的任务与倒计时展示不完整（P1）

只读取第一页 20 条订单，只用 `find` 展示一笔待接单任务；“今日履约日程”没有按日期过滤。倒计时只是固定“120 秒”文案，没有根据 deadline 更新或到期禁用，也没有页面停留期间的任务刷新。

位置：[workbench.js](../miniprogram/pages/staff/workbench.js#L50)、[workbench.wxml](../miniprogram/pages/staff/workbench.wxml#L23)。

修复：提供按人员、日期和状态过滤的任务接口，展示全部待接单项；按服务端期限计算剩余时间，在页面显示期间刷新并正确清理计时器。

### F8. 环境和登录态管理尚不完整（P1/P2）

小程序固定请求 `http://localhost:8080/api`，不能直接作为手机真机访问开发电脑的地址。401 处理只清理存储，没有清理全局 token、userInfo 和角色；后续请求仍可能继续携带失效 token。管理后台路由守卫只看 token 是否存在，不验证管理员身份。

位置：[app.js](../miniprogram/app.js#L4)、[request.js](../miniprogram/utils/request.js#L23)、[router/index.js](../admin-web/src/router/index.js#L65)。

修复：按环境配置服务地址；统一登录状态清理与重新登录入口；后台登录和路由检查管理员身份，后端仍独立校验权限。

### F9. 表单、列表和资源加载仍需完善（P2）

老人、服务项目、人员等列表多处固定只取 20 或 50 条，缺少分页。编辑表单的必填、格式、时段合法性和保存中状态不统一。管理后台构建产生约 864 KB 的主 JS 和约 1122 KB 的看板 JS，并出现大包提示。

位置：[elders/index.vue](../admin-web/src/views/elders/index.vue)、[services/index.vue](../admin-web/src/views/services/index.vue)、[staff/index.vue](../admin-web/src/views/staff/index.vue)、[package.json](../admin-web/package.json)。

修复：先补分页、表单与错误恢复，再按实际资源组成拆分图表和公共依赖。页面视觉质量尚未进行浏览器或真机验收，不据源码推断最终显示效果。

## 二、后端不足

### B1. 普通请求可以取得管理员身份（P0）

`/auth/mock-login` 被公开放行，没有环境开关或 Profile 限制，默认返回管理员登录结果。注册和首次微信登录还直接采用客户端提交的 `role`，没有强制限定为居民身份。

位置：[AuthController.java](../backend/src/main/java/com/agedcare/modules/auth/controller/AuthController.java#L43)、[AuthService.java](../backend/src/main/java/com/agedcare/modules/auth/service/AuthService.java#L84)、[WebMvcConfig.java](../backend/src/main/java/com/agedcare/common/config/WebMvcConfig.java)。

修复：演示接口仅在明确隔离的演示配置启用；公开注册固定居民身份，管理员或服务人员身份只能通过受保护流程赋予。

### B2. 默认登录校验和对象权限缺失（P0）

拦截器只有看到 `@RequireRole` 时才强制登录；没有注解的方法默认放行。订单详情按 ID 直接组装返回，没有检查本人、家属或人员分配关系。

接单和拒单没有验证操作者是否为目标人员；开始服务、提交履约、评价等也没有完整的订单归属校验。人员状态接口同样缺少本人或管理员限制。服务人员在老人访问检查中被整体放行，可以访问不属于自己任务的老人。

位置：[AuthInterceptor.java](../backend/src/main/java/com/agedcare/common/security/AuthInterceptor.java#L55)、[OrderService.java](../backend/src/main/java/com/agedcare/modules/order/service/OrderService.java#L280)、[DispatchService.java](../backend/src/main/java/com/agedcare/modules/dispatch/service/DispatchService.java#L196)、[ElderProfileService.java](../backend/src/main/java/com/agedcare/modules/elder/service/ElderProfileService.java#L120)。

修复：默认要求登录，仅少量公开接口进入白名单；另外按每个订单、老人、人员和消息对象校验访问关系。角色校验不能替代对象权限。

### B3. 敏感用户字段和密钥边界存在问题（P0）

服务人员与家属 VO 直接嵌套 `SysUser`，实体中的 password、openid 没有响应字段隔离。使用实际 Jackson 自动配置的探针确认 password 会进入 JSON；结合公开人员详情、订单详情，构成敏感字段暴露路径。

配置文件还直接保存了微信 Secret、JWT 签名密钥与数据库密码。此处不记录其具体值。

位置：[SysUser.java](../backend/src/main/java/com/agedcare/modules/user/entity/SysUser.java#L23)、[StaffService.java](../backend/src/main/java/com/agedcare/modules/staff/service/StaffService.java#L162)、[FamilyBindingService.java](../backend/src/main/java/com/agedcare/modules/family/service/FamilyBindingService.java#L143)、[application.yml](../backend/src/main/resources/application.yml#L25)。

修复：使用明确的响应 DTO，只输出允许字段；密钥移至外部配置，轮换已经实际使用或外泄的值。

### B4. 接单、拒单、超时处理没有核验当前派单（P1）

接单先读取并校验 attempt，再等待订单锁，持锁后只检查订单 WAIT_ACCEPT，没有再次确认 `currentDispatchId` 与该记录相同，也没有重新核验 attempt 状态与期限。拒单、超时也缺少对应的当前分配校验。

取消或改派与旧请求交错时，旧派单可能误改当前订单，产生已取消订单被回退、旧记录被接单或新任务被干扰的风险。这一交错风险由源码确认，尚未运行数据库并发复现。

位置：[DispatchService.java](../backend/src/main/java/com/agedcare/modules/dispatch/service/DispatchService.java#L196)。

修复：持锁后核对订单状态、当前派单 ID、人员归属、派单状态和期限，并使用带条件的更新检查影响行数。

### B5. 清空当前派单字段不会按预期写入数据库（P1）

多处 `setCurrentDispatchId(null)` 后调用 `updateById`。该字段没有空值更新配置。用项目依赖初始化 MyBatis-Plus 表元数据，确认其策略是 NOT_NULL，生成 SQL 只有字段非空时才更新。

因此不能依靠这些调用清空数据库中的 `current_dispatch_id`，而调度器又只扫描当前派单字段为空的待派单订单，会影响恢复与重派一致性。

位置：[DispatchService.java](../backend/src/main/java/com/agedcare/modules/dispatch/service/DispatchService.java#L278)、[ServiceOrder.java](../backend/src/main/java/com/agedcare/modules/order/entity/ServiceOrder.java#L43)、[DispatchScheduler.java](../backend/src/main/java/com/agedcare/modules/dispatch/scheduler/DispatchScheduler.java)。

修复：对必要清空操作使用明确 SET NULL 的更新，并在同一事务中维护订单、派单和预留；增加数据库集成测试。

### B6. 幂等只实现了部分判断（P1）

命中幂等键时，只比较老人和服务项目，没有比较下单人、时间、地址和联系人，并且在权限检查之前直接返回旧订单。`request_digest` 字段存在，但未填充和使用；并发插入唯一键冲突也没有转换为稳定的幂等结果。

位置：[OrderService.java](../backend/src/main/java/com/agedcare/modules/order/service/OrderService.java#L75)。

修复：按用户限定请求键作用域，计算规范化请求摘要；先校验访问资格，再返回既有结果，并处理并发唯一键冲突。

### B7. 派单计算输入与设计口径不一致（P1）

- 小程序没有提交坐标，后端多数情况下填同一个默认坐标，真实不同地址会被当作同一地点计算。
- 服务区域检查对包含“阳光”的人员区域直接放过，不能形成可靠区域约束。
- 质量分在评价后已经平滑存储，评分引擎又平滑一次，且使用完成订单数代替评价数量。
- 负载按含路程的 booking 起止累计，没有使用已完成服务的实际时长，与文档定义不同。
- 后续路程与下一笔已经包含路程的预留开始时间比较，会重复预留路程，可能排除原本可行的任务。
- 评分上下文没有完整保存权重、先验、实际占用时长与排班输入，固定写 `v1.0` 不足以复现不同配置下的结果。

位置：[OrderService.java](../backend/src/main/java/com/agedcare/modules/order/service/OrderService.java#L129)、[DispatchScoreEngine.java](../backend/src/main/java/com/agedcare/modules/dispatch/service/DispatchScoreEngine.java)、[FulfillmentService.java](../backend/src/main/java/com/agedcare/modules/fulfillment/service/FulfillmentService.java#L219)。

修复：先统一位置、班次、服务时长和评分统计模型，再开展权重调优与策略实验。

### B8. 排班与履约事实管理不完整（P1）

排班添加只判断结束是否早于开始，允许零时长与重叠班次；评分引擎只取第一个班次。技能删除、人员状态变更未按文档阻止影响既有任务的修改，也未采用同一人员锁协议。

开始服务没有持久化独立的实际开始时间；服务超时仍主要按计划结束时间推算人员可用性，未实现文档所述延迟提示与后续协调。

位置：[StaffService.java](../backend/src/main/java/com/agedcare/modules/staff/service/StaffService.java#L130)、[DispatchScoreEngine.java](../backend/src/main/java/com/agedcare/modules/dispatch/service/DispatchScoreEngine.java#L176)、[FulfillmentService.java](../backend/src/main/java/com/agedcare/modules/fulfillment/service/FulfillmentService.java#L61)。

修复：统一修改锁协议与有效任务校验，校验非零且不重叠的班次，正确处理多班次、实际开始时间和进行中服务超时。

### B9. 微信新用户和账号停用处理存在缺口（P1）

首次微信注册一律写空字符串 phone，而数据库 phone 有唯一索引，多个未绑定手机号的微信用户会发生唯一键冲突。新微信用户还被赋予统一已知密码。

JWT 解析仅使用 token 内身份，没有复查账号启用状态；停用账号后已有 token 缺少即时失效机制。微信登录已有用户也未像密码登录一样检查停用状态。

位置：[AuthService.java](../backend/src/main/java/com/agedcare/modules/auth/service/AuthService.java#L129)、[JwtTokenProvider.java](../backend/src/main/java/com/agedcare/common/security/JwtTokenProvider.java)、[schema.sql](../sql/schema.sql#L28)。

修复：未绑定手机号使用明确的空值模型，微信账号无密码时不开放已知默认口令；建立账号停用与 token 校验的一致规则。

### B10. 查询、通知、日志和部署尚需补齐（P2）

- 订单列表逐条装配老人、人员、班次、记录、评价与日志，存在大量 N+1 查询。
- 人员姓名在分页之后过滤，搜索结果与 total 不一致，并可能漏掉其他页中的匹配人员。
- 通知服务存在，但核心派单与履约流程没有调用发送逻辑；操作审计日志只有 SQL 表，未见相应写入实现。
- 业务异常通常仍使用 HTTP 200 返回业务错误码，数据库约束错误和日期解析错误缺少明确映射，接口契约有待统一。
- 数据库脚本以 DROP TABLE 初始化，尚未形成保留数据的版本迁移与恢复流程。

位置：[OrderService.java](../backend/src/main/java/com/agedcare/modules/order/service/OrderService.java#L272)、[StaffService.java](../backend/src/main/java/com/agedcare/modules/staff/service/StaffService.java)、[NotificationService.java](../backend/src/main/java/com/agedcare/modules/notification/service/NotificationService.java)、[GlobalExceptionHandler.java](../backend/src/main/java/com/agedcare/common/exception/GlobalExceptionHandler.java)、[schema.sql](../sql/schema.sql)。
