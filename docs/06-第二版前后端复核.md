## 二、必须优先修复的问题

### R1. [P0] 服务项目通配白名单绕过管理员权限（新问题）

`WebMvcConfig` 新增 `/service-items/*` 排除规则，它同时匹配项目详情、`/service-items/page` 和 `/service-items/save`。被排除的请求完全不执行 `AuthInterceptor`，因此 Controller 上的 `@RequireRole(ADMIN)` 也不会被检查。

使用实际 WebMvcConfig、AuthInterceptor、ServiceItemController 和异常处理器搭建隔离 MockMvc 环境，未携带登录凭据执行保存请求，结果为业务码 200，且已验证写入 Service 方法被调用。对比另一个没有被通配排除的项目管理接口，相同匿名请求被拒绝。

探针中的 Service 是 mock，没有向数据库写入项目。

位置：[WebMvcConfig.java](../backend/src/main/java/com/agedcare/common/config/WebMvcConfig.java#L26)、[ServiceItemController.java](../backend/src/main/java/com/agedcare/modules/serviceitem/controller/ServiceItemController.java)。

建议：公开权限按 HTTP 方法和明确路径区分，只允许必要 GET 读取；管理写接口继续经过登录、角色及对象权限校验。为匿名保存及居民保存各补一条拒绝用例。

### R2. [P1] 开始服务时插入的记录不满足数据库非空约束（新阻塞）

新版 `startService` 在开始时插入服务记录，用于保存实际开始时间，但该记录没有 `actualEndAt` 和 `serviceSummary`。当前 SQL 仍要求 `actual_end_at`、`service_summary` 为 NOT NULL 且没有默认值。

隔离调用实际 FulfillmentService，并捕获传给 Mapper 的插入对象，确认两个字段均为空。按仓库提供的表结构，首次开始服务会因缺少必填字段失败；该方法的事务将回滚，订单无法正常进入服务中。

位置：[FulfillmentService.java](../backend/src/main/java/com/agedcare/modules/fulfillment/service/FulfillmentService.java#L103)、[schema.sql](../sql/schema.sql#L276)。

建议：明确进行中的服务记录允许缺少结束信息，完成时再做完整校验；或将开始事实保存到独立字段/事件，完成时创建完整记录。需要同时提供新库与旧库迁移方案。

### R3. [P0/P1] 模拟身份仍默认开放，微信登录存在未受开关控制的降级

- `app.dev-mode` 的代码默认值和配置默认值仍为 true，默认启动允许免密选择管理员演示账号。已增加开关，但尚未形成默认关闭的边界。
- `fetchWechatOpenid` 在 AppID 或 Secret 缺失时直接返回 `mock_openid_ + code`，不检查 devMode。
- 隔离探针将 devMode 设为 false、微信配置设为空，使用非真实微信 code，实际 AuthService 仍生成了模拟身份并成功返回登录结果。相同条件下 `mockLogin` 本身确实会拒绝，说明仅保护了其中一个入口。

位置：[AuthService.java](../backend/src/main/java/com/agedcare/modules/auth/service/AuthService.java#L41)、[AuthService.java](../backend/src/main/java/com/agedcare/modules/auth/service/AuthService.java#L167)、[application.yml](../backend/src/main/resources/application.yml#L27)。

建议：正常配置默认关闭模拟登录，微信配置缺失时明确报错。确需演示时，单独且显式开启模拟能力，并让所有模拟身份入口遵循同一边界。

### R4. [P0] Secret 环境变量仍带非空敏感默认值

微信 Secret 和 JWT Secret 已改为环境变量表达式，但两者仍带非空字面默认值，秘密仍保存在项目配置中。缺少环境变量时会继续使用这些值，不能视为完成了源码秘密移除。

位置：[application.yml](../backend/src/main/resources/application.yml#L33)、[application.yml](../backend/src/main/resources/application.yml#L53)。

建议：移除真实秘密和可用于正常运行的默认签名密钥，正常启动时校验必要配置，轮换已经实际使用或外泄的值。本报告不重复记录其具体内容。

### R5. [P1] 人员工作状态仍可被无关居民修改

`StaffController.updateStatus` 仅依赖全局登录，没有角色或本人关系校验。`StaffService.updateStaffStatus` 仍按请求中的人员 ID 直接更新。

隔离探针设置当前用户为普通 RESIDENT，对另一个用户的人员档案调用真实 StaffService，更新能够进入 Mapper，状态变为 RESTING。

位置：[StaffController.java](../backend/src/main/java/com/agedcare/modules/staff/controller/StaffController.java)、[StaffService.java](../backend/src/main/java/com/agedcare/modules/staff/service/StaffService.java#L86)。

建议：管理员或该人员本人才能修改；状态使用枚举白名单，并检查变更对有效任务的影响。

### R6. [P1] 家属首次绑定既有老人仍然缺入口

家属页面继续从 `/elders/my-list` 获取可申请对象，该接口只返回本人或已经授权的老人。新家属没有授权时仍无法找到已有老人进行首次申请。

新增建档归属改善了“新建后不可见”，但代管档案自动写 APPROVED 也改变了原定管理员审核流程，需要明确业务规则，不能把自动批准新档案当作已有老人绑定流程的替代。

位置：[family.js](../miniprogram/pages/user/family.js#L33)、[ElderProfileService.java](../backend/src/main/java/com/agedcare/modules/elder/service/ElderProfileService.java#L106)。

建议：使用绑定码或管理员定向邀请，区分本人建档、代管建档和绑定已有老人三种操作。

### R7. [P1/P2] 提交成功到跳转之间仍可再次创建订单

提交中短路、disabled 和同一请求键重用已经加入。但成功回调立即清空请求键并将 submitting 设为 false，然后等待一秒跳转。这一秒内再点击，会生成新键并再次创建订单。

Node VM 探针保留延迟跳转，依次模拟成功后的再次点击，实际产生两次 POST，且请求键不同。

位置：[create.js](../miniprogram/pages/order/create.js#L155)。

建议：成功后保持提交完成状态，按钮继续禁用，直到页面离开；失败重试与修改预约意图的幂等键生命周期分别处理。

建议顺序：先处理 R1 与 R2，再收紧模拟身份、秘密配置和对象权限；之后用数据库及微信真机跑通一笔完整订单，再推进算法实验和界面优化。
