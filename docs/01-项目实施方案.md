# 项目实施方案

文档状态：初始设计基线，尚未进入编码阶段。

## 1. 目标与边界

系统解决社区居家养老服务的预约、人员分配、履约跟踪和服务反馈问题。核心研究问题是：在技能、服务区域和排班约束下，如何兼顾预计出行时间、服务质量和人员工作量进行可解释派单。

首版按单人开发、约十二周、一个社区规划。周数为相对工作安排，不代表学校规定的提交日期。

### 1.1 服务范围

| 服务类别 | 首版项目示例 | 主要业务参数 |
| --- | --- | --- |
| 助餐送餐 | 将餐食送至约定地址 | 预计时长、服务价格、配送区域 |
| 居家保洁 | 约定范围的上门清洁 | 预计时长、技能要求、服务说明 |
| 代买代办 | 购买生活物品、办理一般生活事务 | 预计时长、服务说明、费用说明 |
| 陪同办事 | 陪同处理一般生活事务 | 服务时长、地点、所需技能 |

首版不实现商品采购结算、医疗诊断、专业护理决策和急救调度。服务价格与代购物品金额分开，首版仅管理平台服务费用。

### 1.2 实现范围

- 必须完成：账号权限、老人档案、家属授权、服务项目、人员技能与排班、预约订单、人工派单、自动派单、履约记录、确认与评价。
- 闭环完成后补充：投诉处理、站内通知、统计分析和管理操作日志。
- 扩展功能：真实支付、地图路线服务、微信订阅消息、周期性预约、多社区管理。

## 2. 终端与技术架构

| 组成 | 技术方向 | 职责 |
| --- | --- | --- |
| Java 后端 | Java 21、Spring Boot、MyBatis-Plus | 接口、权限、事务、订单与派单规则 |
| 微信小程序 | 微信原生小程序 | 居民预约、家属代约、服务人员操作 |
| 管理后台 | Vue 3、Element Plus | 项目与人员管理、人工调度、异常处理 |
| 关系数据库 | MySQL | 保存业务事实、排班预留、派单任务和历史 |
| 数据图表 | ECharts | 服务需求、订单进度、人员工作量分析 |
| 测试 | JUnit、Spring Boot Test | 业务规则、接口、权限和事务验证 |
| 部署 | Nginx、Java 应用、MySQL | 演示与运行环境 |

采用模块化单体架构。后端按认证、居民档案、服务项目、人员排班、订单、派单、履约、评价、统计划分模块。

前端只负责交互与展示，权限、金额、状态流转、候选筛选和评分均以后端为准。第一版采用单实例应用，派单状态持久化到数据库，由定时任务处理待派单与接单超时；后续如增加应用实例，需继续验证任务竞争与幂等。

具体版本在初始化时锁定，先完成编译、数据库访问、权限拦截和分页兼容性验证。官方依赖参考：

- [Spring Boot 系统要求](https://docs.spring.io/spring-boot/system-requirements.html)
- [MyBatis-Plus 安装与对应 Starter](https://baomidou.com/getting-started/install/)

微信账号、正式运行所需接入条件及第三方地图能力，在第一阶段按实际账号核验。演示用登录或距离估算若采用替代实现，必须在界面、说明和论文中标明。

## 3. 时间与预约模型

首版使用固定预约开始时间，项目预计时长决定预约结束时间。所有业务时间按北京时间解释，数据库存储约定在建表时统一，后端、定时任务和前端采用同一约定。

可行安排必须位于人员工作班次内，且满足前一项任务至本单、本单至后一项任务的出行时间要求。服务时段使用左闭右开区间 `[开始时间, 结束时间)`，相邻服务是否可衔接仍需检查路程和缓冲时间。

距离计算只在服务区域内有意义。首版可使用统一坐标来源的经纬度计算直线距离，再按固定速度与缓冲时间估算出行时间；该模型属于估算，不能称为真实道路导航。人员当日首单从其配置的服务站点出发，其他预约从前一单地点推算，不能统一使用人员当前定位。

## 4. 智能派单方法

### 4.1 订单顺序

首版按预约开始时间升序，再按创建时间和订单 ID 升序处理等待订单。暂不开放居民自行设置紧急等级。

订单优先级决定先处理哪笔订单；候选人员得分决定同一订单分给谁，两者分别设计。

### 4.2 硬约束筛选

候选人员必须同时满足：

1. 账号正常、服务人员审核通过。
2. 具备该服务项目要求的全部技能。
3. 服务地址属于其服务区域。
4. 预约及必要出行安排处于可工作时间内。
5. 与有效排班预留不存在冲突。
6. 当前时间仍允许其按预计路程和缓冲要求到达。

技能和排班不可行的人员不会进入评分。服务项目未配置技能要求时，该项不额外限制。

### 4.3 多因素评分

初始模型：

```text
Score = 0.35 × D + 0.30 × Q + 0.25 × L + 0.10 × F
```

| 指标 | 含义 | 首版定义 |
| --- | --- | --- |
| D | 到达便利程度 | `1 - min(预计到达路程分钟数 / 30, 1)` |
| Q | 服务质量 | 平滑后的历史平均评分，再从 1～5 映射到 0～1 |
| L | 当日工作量余量 | `max(0, 1 - (当日已有预留服务分钟数 + 本单分钟数) / 当日可工作分钟数)` |
| F | 服务熟悉程度 | 曾为该老人完成服务为 1，否则为 0 |

质量分使用统一先验：先验评分 4 分、先验样本数 5；有 n 条评价、评分总和为 s 时，平滑评分为 `(s + 5 × 4) / (n + 5)`。该参数属于初始假设，实验时可调整并记录。

工作量包含待接单预留、已接单任务与当日已实际发生的服务时长，避免完成订单后工作量被清零；已经释放的预留不再计入。实际完成任务使用实际时长，未完成任务使用计划时长；跨日任务首版不开放预约。该指标用于平衡服务工作量，出行时间可行性由硬约束单独检查。

评分相同依次比较预计路程、当日已有服务时长、人员 ID，保证结果可复现。权重、先验与出行参数统一配置并保存算法版本。该方法属于启发式分配，不宣称获得全局最优解。

### 4.4 顺序派单与恢复

- 每次向一名候选人员发送派单并创建时间预留。
- 默认接单期限为 120 秒，超时扫描间隔为 10 秒；均为首版可配置参数。
- 单笔订单最多进行三次自动派单尝试；尝试次数和已尝试人员以数据库记录为准。
- 拒单或超时后释放预留，在剩余未尝试人员中按最新安排重新筛选和评分。
- 没有候选、尝试次数用尽，或已无法按时到达时，进入待人工处理。
- 人工处理后重新启动自动派单时创建新调度轮次，保留原轮次记录。
- 接单期限不替代时间可行性判断；无法在预约开始前到达的候选不能获得派单。
- 重启后扫描数据库中的待处理订单及过期派单，安全恢复执行。

### 4.5 可解释记录

保存每轮候选、排除原因、指标值、权重、综合得分、选中人员和结果。出行估算值及排班输入也要保留足够的摘要，以便解释当时选择。

后台显示推荐原因和失败原因。人工改派必须填写理由；操作不能绕过技能、时间和排班硬约束。

## 5. 实验方案

比较三种派单策略：合格人员轮询、合格人员距离优先、多因素综合评分。所有策略使用相同的技能、服务范围、时间与出行约束。

建议数据规模为 20 名人员与 200 笔订单、50 名人员与 1000 笔订单，并分别构造需求集中、技能稀缺、排班紧张等场景。使用合成身份资料，并明确实验数据来源。

实验按订单实际到达时间推进仿真时钟，同一策略只能使用当时已知的信息。每种策略在独立初始状态下运行，不能共用已被上一策略修改的排班。

| 指标 | 定义 |
| --- | --- |
| 分配成功率 | 在规定时间内获得可行安排的订单数 / 全部有效实验订单数 |
| 准时率 | 在约定开始时间与配置容忍值范围内开始服务的订单数 / 已实际开始服务订单数；同步报告未开始数量 |
| 平均预计出行时间 | 成功分配任务产生的预计路程总时间 / 相应任务数 |
| 负载差异 | 各人员工作利用率的标准差；只对有可工作时长的人员统计 |
| 重派次数 | 首次派单后再次分配的次数，另报失败原因 |
| 算法计算耗时 | 候选查询、可行性筛选与评分所用时间，注明计时范围 |
| 接单等待时间 | 提交至有效接单之间的时间，与计算耗时分开记录 |

没有有效分母时结果记为不适用，不记为 0。准时容忍值初始为 0 分钟，改变时在实验配置中记录。

固定并保存随机种子、输入、配置、运行环境和原始输出。若模拟拒单和服务时长波动，使用可复现的事件规则。比较不同权重时至少保留一组不参与调参的场景，避免仅对单组数据取得优势。
