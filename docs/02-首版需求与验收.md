# 首版需求与验收

文档状态：待实现需求。所有验收项当前均未执行。

## 1. 角色与数据范围

首版账号分为居民、服务人员、管理员三种主要技术身份。居民根据本人老人档案和已确认的家属绑定关系，承担老人或家属业务角色。多身份账号切换作为后续扩展。

| 业务角色 | 可访问范围 | 关键限制 |
| --- | --- | --- |
| 老人 | 本人档案、本人订单、本人评价 | 不访问其他老人资料 |
| 家属 | 已审核授权老人的必要档案与订单 | 绑定未通过或已撤销时不获得相应访问权 |
| 服务人员 | 本人排班、派给本人的任务、本人服务记录 | 不查询其他人员订单；详细联系方式在有效接单后开放 |
| 管理员 | 本社区业务与管理记录 | 关键处理操作需保留操作者与原因 |

家属提交绑定申请，由管理员核验并确认。老人可以没有小程序账号，由家属代约。绑定撤销后，历史业务记录仍保留，但家属不再据此读取老人资料或订单详情。

## 3. 订单状态与转换

| 状态码 | 页面名称 | 含义 |
| --- | --- | --- |
| WAIT_DISPATCH | 待派单 | 等待自动或人工分配 |
| WAIT_ACCEPT | 待接单 | 已有一条有效待接单派单及相应时间预留 |
| WAIT_VISIT | 待上门 | 服务人员已有效接单 |
| IN_SERVICE | 服务中 | 人员已开始服务 |
| WAIT_CONFIRM | 待确认 | 人员已提交服务记录 |
| COMPLETED | 已完成 | 老人或授权家属确认完成 |
| WAIT_MANUAL | 待人工处理 | 暂时无法自动取得可行安排 |
| CANCELLED | 已取消 | 服务开始前按规则取消 |

| 当前状态 | 操作或事件 | 目标状态 | 约束 |
| --- | --- | --- | --- |
| WAIT_DISPATCH | 选中人员并预留成功 | WAIT_ACCEPT | 事务中复查技能、排班和到达可行性 |
| WAIT_DISPATCH | 无候选或达到尝试上限 | WAIT_MANUAL | 保存失败原因 |
| WAIT_ACCEPT | 有效人员在期限内接单 | WAIT_VISIT | 派单仍为当前有效记录 |
| WAIT_ACCEPT | 拒单或超时 | WAIT_DISPATCH 或 WAIT_MANUAL | 先使本次派单失效并释放预留，再决定是否重派 |
| WAIT_MANUAL | 管理员派单 | WAIT_ACCEPT | 仍需满足硬约束 |
| WAIT_MANUAL | 管理员重新调度 | WAIT_DISPATCH | 记录原因，创建新轮次 |
| WAIT_VISIT | 本人开始服务 | IN_SERVICE | 记录实际开始时间 |
| WAIT_VISIT | 管理员因无法履约撤销分配 | WAIT_DISPATCH 或 WAIT_MANUAL | 保留原接单事实，释放未使用预留 |
| IN_SERVICE | 本人提交服务记录 | WAIT_CONFIRM | 校验实际开始结束时间及必填记录 |
| WAIT_CONFIRM | 老人或授权家属确认 | COMPLETED | 记录确认人和时间 |
| WAIT_DISPATCH、WAIT_ACCEPT、WAIT_VISIT、WAIT_MANUAL | 有权限用户取消 | CANCELLED | 同事务结束有效派单并释放未使用预留 |

已完成和已取消为订单终态，后续评价、投诉使用独立记录。服务开始后不走普通取消；异常作为事件记录，由管理员跟进，保持已经发生的履约事实。

首版不自动确认完成。老人或家属无法操作时，管理员可依据核验结果代为确认，但必须记录代确认身份、依据和原因。

## 4. 核心业务规则

### 4.1 预约

- 必须选择已上架项目、合法服务对象和有效地址。
- 预约开始时间必须晚于当前时间与配置的最小提前量之和；初始提前量为 30 分钟。
- 服务时长与价格由后端读取项目配置，并在下单时保存快照。
- 同一请求幂等键重复提交返回同一订单；相同幂等键对应不同内容时拒绝处理。
- 首版服务在同一天内完成，不开放跨日预约。
- 修改已下单订单的时间、地点或项目，首版采用取消后重新预约，避免旧评分和排班预留继续有效。

### 4.2 派单与排班

- 人工派单和自动派单共用可行性校验与预留逻辑。
- 待接单和已接单任务均占用排班资源，拒单、超时、取消或撤销后释放。
- 单笔订单同时最多一条有效分配；人员不能获得时间或出行安排冲突的预留。
- 默认每轮最多三次自动尝试，优先选择本轮未尝试的人员；每次尝试前重新核验安排。
- 排班、服务范围、技能或账号状态变更如果影响现有有效任务，应阻止直接变更并提示先处理受影响任务。
- 预估结束时间与实际履约时间分开保存。服务超出计划时长时保留异常事实，提示管理员处理后续受影响任务，不能仅凭计划结束时间认定人员已空闲。
- 修改权重只作用于后续计算，不覆盖历史评分。

### 4.3 履约与反馈

- 仅当前有效接单人员能开始服务和提交履约记录。
- 服务记录包括实际开始、结束时间及服务说明；照片为可选项。
- 重复开始、重复提交、重复确认应返回明确结果，不重复生成业务记录。
- 每笔已完成订单最多一条有效评价，评分为 1～5 的整数。
- 统计口径注明时间范围和订单状态，取消订单不计入完成订单数量。

## 6. 验收场景

| 编号 | 场景 | 通过标准 |
| --- | --- | --- |
| AC-01 | 老人本人预约并完成服务 | 下单、人工派单、接单、开始、记录、确认、评价完整可用 |
| AC-02 | 家属代约 | 已审核授权可操作；未授权和撤销授权均不能读取对应数据 |
| AC-03 | 自动派单 | 同一输入按已配置规则产生可解释结果，硬约束不被评分覆盖 |
| AC-04 | 人员拒单 | 原派单失效、预留释放、原因可查，下一次候选按最新安排计算 |
| AC-05 | 接单超时 | 过期记录不能再接单；按上限重派或转人工 |
| AC-06 | 排班与路程冲突 | 时间重叠、路程不足以及影响下一单的情况均能被识别 |
| AC-07 | 两个订单竞争同一人员 | 事务完成后仅保留可行安排，其余重新选择或转人工 |
| AC-08 | 超时与接单同时发生 | 只产生一个有效结果，无同时接受与释放的矛盾 |
| AC-09 | 重复提交或重复任务执行 | 不重复建单、不重复派单、不重复确认 |
| AC-10 | 跨用户修改订单 ID | 后端拒绝越权访问，敏感字段不泄露 |
| AC-11 | 取消待接单订单 | 订单取消、派单撤销和预留释放一致完成 |
| AC-12 | 待接单时应用重启 | 重启后能继续处理且不会创建重复有效派单 |
| AC-13 | 无合格人员 | 显示待人工处理及具体原因，管理员可继续处置 |
| AC-14 | 实际服务超时 | 实际时长正确记录，后续受影响安排有异常提示 |
| AC-15 | 新服务人员没有评价 | 使用统一先验，不出现空值异常或除零 |

功能实现后使用真实接口与数据库验证关键事务；算法单元测试覆盖约束、归一化、冷启动和稳定排序。以上场景不是已经通过的测试结果。
